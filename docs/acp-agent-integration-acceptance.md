## Implemented contract

ACP profiles select a backend, executable, exact argument vector, optional launch directory, literal or backend-environment variable values, and callback policy. Secrets should use a backend environment reference such as `KEY=$BACKEND_VARIABLE`; they are resolved on the backend that starts the agent and are not copied into Monitor's store or sent to another backend. Connection identity is based on profile ID and effective launch configuration, not the display name. Discovery connections cannot mutate filesystem or terminal state.

The backend advertises only the callback capabilities implemented in that build and enabled by the profile. Filesystem policy is `disabled`, `read_only`, or `read_write`; command-terminal policy is `disabled`, `ask`, or `allow`; profiles can add absolute approved roots. Filesystem callbacks are Unix-only. Paths are constrained to canonical approved roots and reject symlink components; reads and writes are UTF-8 text with a 2 MiB bound. Writes are atomic, serialize through the shared file service, and retain a preimage under `acp-file-backups` outside approved roots. The durable callback receipt records pre- and post-write hashes and the backup reference; the ACP wire response follows its protocol result shape. The callback policy constrains these Monitor callbacks; it does not sandbox the agent's own tools or the backend user's permissions.

With command-terminal callbacks enabled, the agent can create, wait for, read, kill, and release processes rooted in an approved directory. `ask` requires a Monitor approval; `allow` proceeds without that prompt. Output is a bounded UTF-8 tail (up to 1 MiB). Command-terminal snapshots and release state are durable in the run store. Authentication terminals are a separate PTY service: terminal auth launches the agent-advertised command and arguments on the executing backend, supports bounded output reads and sequenced input/resize/close operations, reaps its child, and does not persist PTY input or output in the callback journal.

Mutating callbacks write intent before the external side effect and persist the terminal result afterward. Their idempotency key includes connection, generation, ACP request ID type/value, method, parameters, and bound session. Exact completed repeats return the saved wire result; an identity conflict is rejected. A pending/uncertain callback is never blindly replayed because SQLite and an external file write/process launch cannot share an atomic transaction. Connection close marks pending callback outcomes uncertain, cancels in-flight auth operations, closes auth PTYs, stops callback terminals, and stops the ACP process. `close_connection` rejects a stale generation and closes only that generation. Backend shutdown drains connections and operations, terminates login terminals, closes callback services, and stops clients before the store/backend exits. Source-5 fixture acceptance passed the same-connection cancel/follow-up and shutdown scenarios; native-client acceptance is tracked separately below.

Schema 4 adds `acp_callback_operations` and `acp_terminal_snapshots` to `runs.sqlite3`. Upgrades from schema 1, 2, or 3 create a unique `runs.schema<version>-backup-<uuid>.sqlite3` using SQLite `VACUUM INTO` before migration. The source-5 service receipt reports schema-3-to-4 migration, byte-exact prior payloads, and clean integrity on both daemon stores. An older binary cannot open a newer schema; return to schema 3 only after stopping both processes and restoring the preserved schema-3 backup. A schema-4 downgrade restore has not been exercised.
